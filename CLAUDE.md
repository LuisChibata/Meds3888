# Thera-Fits: MEDS3888 G13 (Lived Experience)

USYD design project. A website prototype that helps 18–24-year-olds who have **not yet started therapy** find a therapist who fits them. Self-management is out of the MVP. Luis builds the prototype; the rest of the group (Allysa, Auriel, Gabriella, Shahad, Vanessa) does research and questions; supervisor is Dr Belal Chami. The site is called "Thera-Fits" (renamed from the working name "FIT-FIRST" on 15/10).

## Project rules (decided by the group, don't re-litigate)
- **MVP scope: matchmaking only, patient-focused.** 8 fictional therapists as plain seeded data in their own file. No therapist account, no self-management (questionnaire Q11–Q15 are out of the flow). Verify matching against fictional test patients, not by eye.
- **Demo only.** All therapist data is fictional and badged "Fictional demo profile". No backend, nothing leaves the page. Keep the footer disclaimer and the Lifeline 13 11 14 / 000 line.
- **Not clinical.** No symptom or diagnosis questions, no advice. Plain, neutral lay language, no mental-health labels in questions (participants self-categorise at the end). Australian English.
- **Keep it simple.** Few features. Each one must trace back to interview or Google Form evidence. Website, not native app.
- **Matching follows the research doc** (`compass_artifact_…_text_markdown.md`, section "Recommendations"): risk screen first and it overrides matching; weight therapists' self-reported specialties low (they oversell); shortlist of 2–3; patient preferences are the last layer; never publicly rank therapists; any outcome data is synthetic and labelled as such.

## Design decisions (Luis; carry these forward)
- **Matching is decoupled from the website** (14/10). A page never scores anything: it passes answers and therapists to a ranking system and draws what comes back. Ranking systems are swappable, one file each, registered with `FF.rankers.register()` and following the contract at the top of `Explainer/matching/rankers.js` (filters with reasons, an optional group, weighted parts with plain-language "said" / "has"). Ranking systems don't sort: `FF.rankers.run()` does, the same way for all of them, so the explanation on screen is always true. New matching work follows this, including any port of `App/`, which predates it and still calls `FF.match` directly.

## Layout
- `index.html` (repo root): **the front page** (15/10). Plain HTML, no React: explains the premise (why, how matching works, demo-only), then links to `App/` and the walkthrough (`Explainer/story.html`, with "or explore the details" for `Explainer/index.html`; that link sits above the card-wide link so it stays clickable). Their headers link back ("About", or the logo). Same colour tokens. Its claims come from the meeting notes and the research doc; keep them in step with those.
- `netlify.toml`: publishing. A push to `master` deploys Netlify site `thera-fits` (https://thera-fits.netlify.app). Only `index.html`, `App/` and `Explainer/` are copied, keeping the repo's folder names so relative links work from file:// and online. Netlify paths are case-insensitive and redirect to lower case (`/App/` → `/app/`). A new top-level folder isn't published unless the build command changes.
- `App/`: **the basic prototype** (MVP foundation, the full 15-question flow). No build step; classic `<script>`s sharing a global `FF` namespace (ES modules don't load from file://), so load order in `index.html` matters.
  - `src/data/questions.js`: Q1–Q10, Q16–Q20 with option ids. Wording copied from the workflow doc; change it there first.
  - `src/data/therapists.js`: the 8 fictional therapists. Fields must use the option ids from questions.js (tests.html checks this).
  - `src/data/test-patients.js`: patients A–E with expectations.
  - `src/matching.js`: pure engine, `FF.match(answers, therapists)` → `{ status, shortlist, closest, ranked }`. Weights and the sourced evidence pairings are constants at the top.
  - `src/ui.js` (building blocks from the prototype), `src/app.js` (flow: landing → safety → one question per screen → results).
- `Explainer/`: **the matching explainer** (14/10; profiles and check-ins 21/10; walkthrough 22/10). Same stack and colour tokens as `App/`; its own data, so changing one prototype doesn't move the other. Two pages on the same `data/` and `matching/`, linked both ways in the header:
  - `story.html`: **the walkthrough**, for anyone (Luis: good enough to be the main way in; the details page stays for the team). An animated story of about 3 minutes, 7 chapters and 25 beats, following "Alex" (test patient A; fictional international student; they/them; a drawn SVG portrait, not a stock photo, because the story ties Alex to anxiety) under Track record with the full synthetic year: answers and profile → therapists' self-description → one real synthetic course's check-ins → the year filling in therapist records → says vs reports → filters, track record, preferences, shortlist, with vs without check-ins → what Alex sees. `site/player.js` is generic (one clock, beats `{ chapter, caption, sr, anim, hold }`, play/step/scrub/chapters, captions in an aria-live region, transcript, reduced motion = no tweening, `?beat=n`). `site/story.js` holds the story: facts read from `FF.rankers.run()` and `FF.records.build()`, captions as templates over them, and a beat whose fact doesn't hold is dropped. Each beat is a frame of actors for when its movement ends, tweened by `FF.player.mix` (numbers tween; missing `o`/`s` mean 1; `enter`, `d` stagger, `linear`, `late`); layouts are computed from the stage size (wide ≥ 720px, else a real phone layout); movement uses inline styles only, never per-frame class changes (the Tailwind CDN would rescan). Alex's portrait colours are `--alex-*` in `story.html`. Therapists are shown by initials, except on chapter 7's shortlist cards ("What Alex sees"), where their stock photos fade in, as on the demo's results page.
  - `index.html`: **the details** (retitled "matching details"), for the team and supervisor, not end users: it ranks therapists openly, and opens with a "Watch the walkthrough" card. It tells three steps: (1) the person's profile, built from six questions (Q6, Q16–Q20), as the plain lines the person would see, plus "try a check-in as this person"; then behind the scenes, under a timeline that replays a synthetic year of check-ins, (2) therapist profiles: what each says next to what patients report, per area, with a detail view per cell; (3) the shortlist: every therapist's filters, group and points, a breakdown, and a switch between ranking systems.
  - `img/therapists/`: copies of `App/`'s 8 Pexels stock photos, with `CREDITS.md`. **Photos only where nothing negative is said about the therapist** (Pexels licence: identifiable people "may not appear in a bad light"). Ben and Riley get negative labels from check-ins, so photos never go in the grid, the records, the matching rows or the set-aside tray; only on the walkthrough's shortlist cards. Fictional people the story ties to anxiety (Alex) get a drawn portrait, never a stock photo.
  - `data/`: the six questions (canonical wording, trimmed options; Q6 options also have short names, ours), the same 8 therapists cut down to the fields used (plus `photo`, not scored), test patients A–E (E is new), `check-ins.js` (the check-in form and a synthetic year of 151 courses generated from a readable `RECIPE` with a fixed seed; the recipe needs group sign-off). `open` in a test patient = an expectation the group hasn't settled; tests report it as OPEN, not FAIL.
  - `matching/`: `rankers.js` (contract, registry, `run`, `check`), `criteria.js` (shared measurements, no weights), `records.js` (profiles from check-ins: per therapist and area, helped / no clear change / got worse / not enough evidence yet, against fixed thresholds; and each person's own progress; no ranking), then one file per ranking system: `research.js` (the working spec), `checklist.js` (naive baseline: equal weights, believes self-listed areas), `access.js` (cost and waiting time first), `track-record.js` (Research-guided plus patients' check-ins; identical to Research-guided with no data). Knows nothing about the page.
  - Ranking systems get `rank(answers, therapists, context)`; `context` is `{ checkIns, week }`. One that reads it sets `usesCheckIns: true` (the page then recomputes when the week or a check-in changes); the others ignore it.
  - `site/`: `theme.css` and `theme.js` (colour tokens and Tailwind config, shared by both pages: change tokens there), `ui.js` (also `RECORD_LOOK`, how each records label looks), `profiles.js` (person profile and its `profileRows`, check-in, timeline, therapist grid, cell detail), `app.js`, then `player.js` and `story.js` for the walkthrough. Never scores or labels: draws what `FF.rankers.run()` and `FF.records.build()` return. Bar colours per kind of points are `--kind-*` in `site/theme.css` (a validated colour-blind-safe palette, in that order; a new kind needs a colour).
  - Adding a ranking system: a new file in `matching/`, plus a `<script>` after `criteria.js` and `records.js` in both `index.html` and `tests.html` (and after any system it builds on: `track-record.js` reads `research.js` when it registers). The first one registered is the default. `story.html` loads only `research.js` and `track-record.js`, the two its story uses.

## Running and checking
No build or package.json. Node is installed on the Linux machine, not on the Windows one; nothing needs it. Open `App/index.html`, `Explainer/story.html`, `Explainer/index.html` (or the prototype) in a browser; needs internet for Tailwind 3.4.16, React 18.3.1 and Google Fonts from CDNs. `App/index.html?patient=A` (A–E) jumps straight to a test patient's results. `Explainer/index.html?patient=A&ranker=access&open=priya` loads a patient, picks a ranking system and opens a breakdown. Also `?view=profiles|shortlist`, `?week=0`–`52` (how far into the synthetic year), `?cell=ben.anxiety` (one therapist's record in one area). The check-ins demo: `?patient=A&ranker=track-record`. `Explainer/story.html?beat=12` opens the walkthrough at step 12, paused, after it has moved.
- **Matching tests:** open `App/tests.html`. Headless from PowerShell (the page title is `PASS n/n` or `FAIL n/n`):
  `& "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe" --headless=new --disable-gpu --user-data-dir="<scratchpad>\edge" --virtual-time-budget=3000 --dump-dom "file:///D:/Luis/uni/meds3888/App/tests.html"`
  On the Linux machine (Chromium), from the repo root; prints just the title:
  `chromium --headless=new --disable-gpu --user-data-dir="<scratchpad>/chr" --virtual-time-budget=5000 --dump-dom "file://$PWD/App/tests.html" 2>/dev/null | grep -o '<title>[^<]*'`
  Run after any change to weights, therapists or questions. Don't edit a test patient's expectation to make it pass; that's a group decision.
- **Explainer tests:** `Explainer/tests.html`, same commands with that path. Title is `PASS n/n (k open)`. Loads only `data/` and `matching/`, no page code. Checks every ranking system against the contract, the research-guided one against the test patients, and that each system's description stays true.
- **Walkthrough:** no test page; it draws only what `matching/` returns. After changing it, look at every beat (`?beat=1`…`25`) at laptop and 390px widths, light and dark, and step through it by keyboard (←/→ and K inside the player) and with reduced motion. For headless screenshots over CDP, scroll the player into view and capture the viewport: `captureBeyondViewport` resizes the page mid-capture, the stage re-measures, and the frame comes out laid out for the wrong width.
- Verify UI changes in a real browser: walk landing → results, in light and dark mode, and by keyboard only. Headless Edge `--screenshot` works for a quick look, but `--virtual-time-budget` can freeze CSS transitions mid-way (selected buttons look unselected); judge colours in a real browser.

## Prototype internals (`documents/FIT-FIRST prototype (1).html`)
- One self-contained file with an inline `<script>`. No JSX or Babel: components are `React.createElement` calls. The prototype gets shared with the supervisor and teammates, so keep `App/` openable by double-click too unless we agree to add a build step.
- Data constants sit at the top: `PRIORITIES`, `PRIOR_CHANGES`, `THERAPISTS`. Every therapist's `align` needs an entry for **every** priority id, or `alignmentFor` throws.
- The flow is a `step` state machine in `App`: landing → intro → prior → select → rank → profile → compare → detail → feedback → done. A new screen needs a `switch` case plus an entry in `STEP_STAGE` (header stage) and, if it is part of the Fit Profile, `FIT_STEPS`.
- Colours are CSS variables holding space-separated RGB, mapped to Tailwind tokens (`paper surface sunken ink muted line accent ochre`). Use the tokens, not hex. Light/dark comes from `prefers-color-scheme` plus `data-theme`; define both when adding a variable.
- Accessibility is deliberate: skip link, focus moves to `#screen-title` on every step change, reduced-motion respected, alignment is never conveyed by colour alone. Don't regress it.
